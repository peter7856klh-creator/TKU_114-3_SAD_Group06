### 任務 2：建立利害關係人分析表
| 利害關係人（stakeholder） | 是否直接使用系統 | 與系統的關係 | 主要需求 / 痛點 | 權力 | 關注 | 分類 |
|---|---|---|---|---|---|---|
| 1.揪團發起人（團主）  |是 | 在系統上開團、填寫出發地、目的地與預估總車資。| 痛點：一個人搭車太貴，傳統社群揪人容易被洗版；成團後每個人要分多少錢很難算。 | 低 | 高|主要使用者 (主要操作者)  |
| 2.共乘加入者（團員） |是  |瀏覽看板、篩選目的地，並點擊一鍵加入揪團。  |需求：能快速找到符合自己時間與目的地的車，且分攤的金額要公開透明。  |低 | 高 | 主要使用者 (主要操作者) |
| 3.課外活動組 / 生輔組（學校行政人員） |否  |負責校內學生校外安全督導，不操作看板，但關切學生揪團安全。  |需求：不希望學生因為揪團遇到詐騙、或因私人金流糾紛鬧到學校行政單位。  | 高 | 中  |外部間接影響者 (非直接操作)  |
| 4.學校大門警衛 / 駐衛警 |否  |負責校門口交通秩序，不操作系統，但受共乘集合影響。  |需求：希望學生在校門口集合上計程車時速度要快，不要讓多台計程車在校門口違停、回堵造成交通混亂。  | 中 | 低 |外部間接影響者 (非直接操作)  |
| 5.合作/排班計程車司機 |否  |在校門口或車站載客的司機，不操作系統，但為服務提供者。  |需求：希望學生上車前就已經確定好人數，且出發前就知道誰要付錢，不要在車上為了算帳卡很久。  | 低 | 中 |外部間接影響者 (非直接操作)  |
| 6.專案開發小組（我這一組） | 否 | 負責本系統的帳號權限管理、看板維護與防呆規則設定。 |需求：必須在 5 週暑修內完成資料庫與網頁功能串接，且 Demo 時系統不能算錯錢或當機。  | 高 | 高 |系統管理與開發者  |
### 任務 3：建立權力 / 關注矩陣
| 類型 | 本組利害關係人 | 溝通策略 |
|---|---|---|
| 低權力、高關注 |揪團發起人（團主）  |優先需求訪談：他是系統活躍度關鍵。開發期間優先收集其發文表單與算帳痛點的反饋，隨時告知開發進度並優化操作流暢度。  |
| 低權力、高關注 | 共乘加入者（團員） |優化操作體驗：他是看板的主要流量來源。設計 UI 時以一鍵加入、直覺瀏覽目的地為核心，盲測時確保其不需要看說明就能順暢使用。  |
| 高權力、中關注 |課外活動組 / 生輔組（學校行政人員）  |定期回報確保合規：平時不干涉網站運行，但需確保系統不涉及校外違法金流，期末成果發表時邀請其觀看，證明系統安全合規。  |
| 中權力、低關注 | 學校大門警衛 / 駐衛警 |宣導配合與被動觀察：他們不操作系統，但在系統公告內主動宣導「校門口集合請迅速上車」，避免共乘造成校門口交通回堵。  |
| 低權力、中關注 |合作/排班計程車司機  |維持現狀與商務流暢：他們深受共乘結果影響。確保系統算出的車資清晰，讓學生上車前就分好錢，加速司機載客與收款的流程。  |
| 高權力、高關注 |專案開發小組（我們這一組）  |全力配合與緊密監控：我們掌控核心代碼與專案時程。需每日對齊進度，確保 5 週內核心功能閉環，Demo 當天系統能穩定跑完流程。  |
### 任務 4：完成可行性分析
| 可行性類型 | 分析內容 | 判斷結果 | 需要調整的範圍 |
|---|---|---|---|
| 技術可行性（technical feasibility） |本組組員具備基本網頁前後端與基礎資料庫的開發能力。若要串接即時地圖導航 API、高併發 Race Condition 鎖定機制或金流系統，技術難度過高，容易導致系統無法按時產出。  | 有風險|縮小範圍：取消地圖 API 串接，地點改由使用者鍵盤打字輸入；車資計算改用純後端數字除法，降低邏輯複雜度。  |
| 操作可行性（operational feasibility） |大學生極度依賴 LINE 發文揪團通勤，對於「共乘」的操作概念非常熟悉。系統介面設計只要像公布欄一樣直覺，一鍵就能加入，使用者不需要任何學習成本就能流暢上手。  | 可行|(無，功能符合大學生日常操作習慣。)  |
| 時程可行性（schedule feasibility） |本專案必須在 5 週暑修時程內完成。如果加上內建即時聊天室與會員星等檢舉評分機制，開發與測試時程絕對會嚴重超支，Demo 當天無法繳出完整成品。  | 有風險 | 調整範圍並移至範圍外：將「內建即時聊天室」與「評價機制」刪除，改為成團後直接顯示彼此的 LINE ID，讓同學私下加群溝通。 |
| 經濟可行性（economic feasibility） |本專案為校園課堂作業，不以營利為目標，組員時間為主要成本。如果串接第三方簡訊通知（SMS） API 或付費 Google Maps API，將會產生組員無法負擔的額外工程費用。  |  有風險 |移至範圍外：不串接收費 API。取消自動發送手機簡訊通知的功能，改由網頁看板內動態重新整理、顯示滿額狀態即可。  |
### 任務 5：建立風險清單第 1 版
| 風險編號 | 風險描述 | 影響 | 可能性 | 應對方式 |
|---|---|---|---|---|
| R1 |【範圍過大】初期功能規劃包含太多第三方 API（如地圖導航、即時通訊、線上支付），導致 5 週內寫不完而爛尾。  | 高 | 高 |嚴格控制邊界：主動在規格書中將金流、地圖、聊天室劃入範圍外項目，改以手動輸入和顯示 LINE ID 替代。  |
| R2 | 【需求資料不足】未實際詢問經常搭計程車通勤學生的真實感受，導致車資分攤計算公式與欄位設計不符校園共乘的拆帳習慣。 | 中  | 中|同儕需求訪談：在第 2 週主動訪談 3 位常搭車的同學，確認他們在拆帳時是採用四捨五入還是無條件進位，並據此撰寫程式邏輯。  |
| R3 |【工具、原型與文件管理】組員程式碼分支管理混亂，或是沒有將進度即時 commit 與 push，造成最後整合時發生嚴重的程式碼衝突或檔案遺失。  | 高  |  中  |落實 Git 規範：每次與 AI 互動、修改完 Markdown 規格書或程式碼後，當天必須使用 GitHub Desktop 進行進度同步，保持 main 分支乾淨。  |
| R4 |【技術熟練度風險】組員對於資料庫 schema 設計與前後端串接工具不夠熟悉，在開發一鍵加入揪團的連動功能時卡關。  | 高 | 中 | 功能精簡化：不設計複雜的多表關聯，改以最簡單的 User 與 Group 兩張基礎資料表進行 CRUD 操作，降低代碼難度。 |
| R5 |【使用者行為風險】上線 Demo 時，若有不守規矩的使用者隨意亂填誇張的車資（如總車資輸入 1 塊錢），導致分攤計算機失去意義。  | 低 | 高 |前端防呆限制：在車資輸入欄位設定限制條件（如總車資必須大於 0 的正整數，或設定基本防呆區間），避免網頁跑出異常數據。  |
