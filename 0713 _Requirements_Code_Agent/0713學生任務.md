## 學生任務

### 任務 1：確認專案章程第 2 版

請打開小組 GitHub 儲存庫中的專案章程第 2 版（Project Charter v2），確認以下內容：

1. 目標使用者（target users）是否明確。
2. 三個原型核心任務（core tasks for prototype）是否仍然合理。
3. 範圍內項目（in-scope）是否能支援需求訪談。
4. 範圍外項目（out-of-scope）是否能限制程式碼代理不要亂加功能。
5. 主要風險（major risks）是否需要在訪談中確認。

完成標準：

- 至少寫出 2 個今天需要確認的需求問題。
- 若專案章程第 2 版需要修正，請先更新再進入訪談設計。

本組確認結果：

- 目標使用者為校園內需要共乘或分攤車資的學生。
- 三個核心任務為：發起揪團、加入揪團、查看分攤金額。
- 範圍內項目包含看板、發起表單、加入流程與分攤計算。
- 範圍外項目包含地圖導航、即時聊天室、金流與正式登入。
- 主要風險包含功能範圍過大、需求理解不足與 AI 產出偏離需求。

### 任務 2：設計訪談大綱

請為至少 2 種利害關係人設計訪談大綱（interview guide）。每種角色至少 6 題。

建議題型：

1. 背景問題。
2. 現況流程問題。
3. 痛點問題。
4. 例外情況問題。
5. 資料需求問題。
6. 權限或責任問題。
7. 通知或回饋問題。
8. 成功標準問題。

完成標準：

- 至少 12 題訪談問題。
- 不可全部都是「你覺得需不需要某功能」。
- 至少 4 題要能問出例外情況或限制條件。

本組訪談大綱：

#### 角色 1：團主（發起人）

| 題號 | 訪談問題 | 想確認的需求或風險 |
| ---- | -------- | ------------------ |
| 1 | 你平常是怎麼發起共乘揪團？ | 確認現況流程與痛點 |
| 2 | 發起揪團時最重要的資訊是什麼？ | 確認欄位需求 |
| 3 | 你最擔心的情況是什麼？例如人數超額、資訊不完整或計算錯誤？ | 確認風險與防呆需求 |
| 4 | 你希望系統在成團後可以自動幫你做什麼？ | 確認自動化與流程簡化 |
| 5 | 你是否希望系統顯示目前加入人數與剩餘名額？ | 確認成團狀態顯示需求 |
| 6 | 如果要做一個簡單的原型，你認為最重要的三個功能是什麼？ | 確認核心任務 |

#### 角色 2：團員（加入者）

| 題號 | 訪談問題 | 想確認的需求或風險 |
| ---- | -------- | ------------------ |
| 1 | 你通常是如何找到共乘對象？ | 確認現況方式 |
| 2 | 你認為一個好的共乘平台最重要的是什麼？ | 確認使用者期待 |
| 3 | 你會希望加入後立刻看到哪些資訊？ | 確認加入後畫面需求 |
| 4 | 你是否會在意每個人要分攤多少錢？ | 確認分攤計算需求 |
| 5 | 若人數已滿額，你希望系統如何處理？ | 確認滿額防呆需求 |
| 6 | 若平台功能太多，你會不會覺得難用？ | 確認簡潔介面與範圍控制 |

### 任務 3：進行模擬訪談並記錄

請小組內或與其他組進行模擬訪談（simulated interview）。每次訪談至少記錄：

1. 受訪角色。
2. 訪談問題。
3. 回答摘要。
4. 追問問題。
5. 可能需求。
6. 不確定處。

完成標準：

- 至少完成 2 個角色的訪談紀錄。
- 每個角色至少 5 筆有效回答。
- 每個角色至少 1 題追問。

本組模擬訪談紀錄：

| 受訪角色 | 問題摘要 | 回答摘要 | 追問 | 可能需求 | 不確定處 |
| -------- | -------- | -------- | ---- | -------- | -------- |
| 團主 | 發起揪團需要填哪些資訊 | 需要填出發地、目的地、時間與人數上限 | 是否需要填總車資？ | 發起表單與預估總車資欄位 | 是否需要地點選單 |
| 團主 | 成團後要不要自動通知 | 簡單顯示狀態即可，不一定要通知 | 是否需要即時更新？ | 狀態更新與剩餘名額顯示 | 通知機制屬範圍外 |
| 團員 | 加入後想看到什麼 | 想知道自己應分攤多少錢 | 是否要看所有成員名單？ | 動態分攤計算與成員清單 | 是否需要聊天室 |
| 團員 | 人數滿額怎麼辦 | 希望系統直接阻止再次加入 | 是否要顯示候補？ | 已滿額防呆 | 候補功能暫不納入 |
| 一般使用者 | 瀏覽看板的需求 | 想快速看到可加入的揪團 | 是否要篩選功能？ | 看板瀏覽與簡單篩選 | 地圖功能先不做 |

### 任務 4：建立需求來源表

請從訪談紀錄與前一週文件萃取需求，建立需求來源表（requirements source table）。

每筆需求至少包含：

1. 來源編號（source ID）。
2. 來源類型（source type）。
3. 來源角色（source role）。
4. 原始摘要（source summary）。
5. 萃取需求（extracted requirement）。
6. 需求類型（requirement type）。
7. 本期是否納入。
8. 對應原型任務。

完成標準：

- 至少 10 筆需求來源。
- 至少 6 筆功能性需求（functional requirement, FR）。
- 至少 2 筆非功能性需求（non-functional requirement, NFR）。
- 至少 2 筆限制條件（constraint）或業務規則（business rule）。
- 每筆需求都要有來源強度：強、中或弱。
- 至少 2 筆需求要保留「不納入本期」並寫明理由。
- 若需求來自生成式 AI（generative AI）或程式碼代理（code agent），不可直接列為強來源。

本組需求來源表：

| 來源編號 | 來源類型 | 來源角色 | 來源強度 | 原始摘要 | 萃取需求 | 需求類型 | 本期是否納入 | 納入或不納入理由 | 對應原型任務 |
| -------- | -------- | -------- | -------- | -------- | -------- | -------- | ------------ | ---------------- | ------------ |
| INT-01 | 訪談（interview） | 團主 | 強 | 發起揪團時需要填出發地、目的地、時間、人數上限與預估總車資 | 系統應提供發起揪團表單，並記錄基本行程資訊 | 功能性需求（FR） | 是 | 這是發起揪團的核心流程 | 發起共乘揪團並同步看板 |
| INT-02 | 訪談（interview） | 團員 | 強 | 加入後希望看到自己應分攤多少錢 | 系統應在加入後重新計算每人的分攤金額 | 功能性需求（FR） | 是 | 此功能與原型核心任務直接相關 | 一鍵加入與動態分攤計算 |
| INT-03 | 訪談（interview） | 團主 | 中 | 團主希望在人數達上限時看到已滿額狀態 | 系統應阻止再次加入並顯示滿額狀態 | 非功能性需求（NFR） | 是 | 可提升流程正確性與使用者理解 | 滿額防呆與狀態顯示 |
| DOC-01 | 文件（document） | 專案章程 | 中 | 專案章程已定義看板、加入、分攤計算與滿額防呆為核心範圍 | 本期原型應聚焦在這四項功能 | 限制條件（constraint） | 是 | 以章程為範圍依據，避免功能過大 | 範圍控制與核心流程 |
| OBS-01 | 觀察（observation） | 校園活動資訊流 | 中 | 目前學生常透過社群張貼資訊，難以即時掌握成團人數 | 系統應提供一個集中、可瀏覽的揪團看板 | 功能性需求（FR） | 是 | 對應看板瀏覽與加入流程 | 首頁看板瀏覽 |
| INT-04 | 訪談（interview） | 團員 | 中 | 團員希望加入後立刻看到剩餘名額與成團狀態 | 系統應在卡片或詳細頁顯示目前人數與空位 | 非功能性需求（NFR） | 是 | 可提升操作信心與透明度 | 卡片與詳細頁顯示 |
| AI-01 | 生成式 AI（generative AI） | 小組自行生成 | 弱 | AI 建議加入地圖導航、即時聊天室與通知功能 | 先做簡單看板與分攤計算，不做外部地圖或即時通知 | 限制條件（constraint） | 否 | 來源強度弱，且與本期範圍不符 | 範圍外控制 |
| INT-05 | 訪談（interview） | 團主 | 強 | 團主希望發起表單資料能即時出現在看板 | 系統應讓新增揪團後立即顯示在首頁 | 功能性需求（FR） | 是 | 這是發起流程的直接結果 | 發起與即時更新 |
| INT-06 | 訪談（interview） | 團員 | 中 | 團員希望加入流程簡單，不要有太多步驟 | 系統應提供一鍵加入或簡化加入流程 | 功能性需求（FR） | 是 | 可提升使用者體驗與原型可操作性 | 加入揪團流程 |

### 任務 6：撰寫程式碼代理實作任務書

請把本組需求整理成程式碼代理實作任務書（code agent implementation brief）。任務書必須讓程式碼代理知道「要做什麼、不做什麼、怎樣算完成」。

任務書至少包含：

1. 專案背景。
2. 目標角色。
3. 第一個可操作切片（first working slice）。
4. 本期範圍內項目（in-scope）。
5. 本期範圍外項目（out-of-scope）。
6. 需求清單。
7. 驗收條件（acceptance criteria）。
8. 技術限制（technical constraints）。
9. 不可捏造事項。

完成標準：

- 不能只寫「幫我做系統」。
- 至少列出 5 個驗收條件。
- 至少列出 3 個程式碼代理不可自行決定的事項。
- 至少列出 3 個範圍外項目，避免程式碼代理自動擴大功能。
- 至少列出 1 個「若代理想加入，必須拒絕」的功能。

本組實作任務書摘要：

- 專案背景：校園揪團與共乘／分攤平台，目標是在有限時間內完成第一個可操作切片。
- 目標角色：團主、團員。
- 第一個可操作切片：團主發起揪團，團員加入後可看到分攤金額，且人數滿額時顯示已滿額。
- 本期範圍內：發起揪團表單、首頁看板、加入流程、分攤計算、滿額防呆。
- 本期範圍外：Google Maps 導航、即時聊天室、簡訊與 Email 通知、線上金流、正式登入與資料庫。
- 驗收條件：看板顯示揪團、表單可送出、加入後可顯示分攤金額、滿額時不可再加入。
- 技術限制：使用 HTML、CSS、JavaScript，使用假資料，不使用正式後端。
- 不可捏造事項：不得新增不存在的角色，不得加地圖或聊天功能。
- 必須拒絕的功能：地圖導航、即時聊天室、線上金流。

### 任務 7：使用程式碼代理建立第一個可操作切片

請使用程式碼代理（code agent）建立第一個可操作切片（first working slice）。如果小組還沒有決定正式技術，可以先做簡單網頁原型：

1. 超文字標記語言（HTML）。
2. 樣式表（CSS）。
3. JavaScript 程式語言（JavaScript）。
4. 假資料（mock data）。

可操作切片需符合：

1. 對應一個核心使用者任務。
2. 有至少 2 個畫面或狀態。
3. 有一個可操作動作，例如新增、送出、查詢、篩選、審核或取消。
4. 有清楚的完成結果。
5. 不需要正式登入、正式資料庫或正式部署。

完成標準：

- 可以在本機或瀏覽器打開操作。
- 至少 1 個驗收條件能被實際操作檢查。
- 程式碼代理產出的內容有人工檢查與修正紀錄。

本組執行結果：

- 已建立包含看板、發起表單與加入流程的簡易網頁原型。
- 可實際操作新增揪團、加入揪團與查看分攤金額。
- 已完成滿額防呆與狀態顯示。
- 產出內容已由小組人工檢查與修正。
